# Production Build Memory

## Measured cause

The Worker is generated by Nitro's Cloudflare module preset. Scheduled and
queue events are handled by Nitro's native `cloudflare:scheduled` and
`cloudflare:queue` hooks; the application does not dispatch those events from a
repository entrypoint.

Measurements from the same `staging` revision on macOS arm64:

| Build | Result | Maximum RSS |
| --- | --- | ---: |
| Nitro 3 Cloudflare build, default V8 heap | Pending remeasurement | — |
| Nitro 3 Cloudflare build, 6,144 MB old-space limit | Pending remeasurement | — |

The Nitro 3 native hooks are the only event-dispatch path. If a build-memory
regression returns, it must be fixed in the Nitro build or reported upstream;
the repository must not add a second scheduler implementation.

The web Worker remains the only deployment unit. A memory regression is a
release-blocking build failure, not a reason to add another Worker or event
dispatch path.

## Build commands

- `yarn build` creates the complete deployable Worker with the required V8 heap.

## Scheduled-task validation

The lowest-level regression suite is:

```bash
yarn test:scheduled-tasks
```

It verifies the cron map, environment and scheduled-time propagation, sibling
failure isolation, and unknown-cron behavior. To exercise the actual Worker
entrypoint after `yarn build`:

```bash
yarn wrangler dev .output/server/index.mjs --assets .output/public --local --test-scheduled --port 8788
curl 'http://127.0.0.1:8788/__scheduled?cron=%2A%2F5%20%2A%20%2A%20%2A%20%2A'
```

The endpoint should return `Ran scheduled event`. Local D1 must be migrated
and seeded before expecting data-dependent task success. Preview and staging
explicitly set `crons = []`; do not use them for scheduled-task smoke tests.
Provider delivery modes must remain `log_only` for local validation.
