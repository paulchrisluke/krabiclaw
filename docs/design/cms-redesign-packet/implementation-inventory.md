# Tenant CMS route and UI-owner inventory

Generated by `node scripts/audit-cms-redesign-inventory.mjs` from 56 Nuxt dashboard routes and 95 CMS packet audit rows.

## Reviewed findings at `ac4430c7`

The packet and source agree on the main redesign problem. KrabiClaw already has focused settings editors, but its content managers use several unrelated interaction models. The redesign should deepen the working shared settings model and decide explicit exceptions. It should not replace every manager with one universal editor.

### Existing canonical owners

- `layouts/dashboard.vue` owns authenticated dashboard chrome, desktop sidebar navigation, mobile bottom navigation, dashboard context, and scope-aware links. Route components should not recreate this chrome.
- `components/dashboard/EditorPaneShell.vue` owns the responsive hub and focused-detail split. Desktop keeps both panes visible. Mobile hides the hub while editing and reserves bottom space for the dashboard navigation. Its footer already provides the reference packet's Cancel and Save placement.
- `components/dashboard/EditorNavigationList.vue` owns grouped settings rows for organization, site, brand, and location settings. Its item type accepts `icon`, but the template does not render that icon. That single omission explains part of the packet's "tight and plain" settings comparison even though callers already provide icon names.
- `components/dashboard/OrganizationSettingsShell.vue`, `lib/components/workspace/settings/SiteSettingsPage.vue`, and `lib/components/workspace/settings/LocationSettingsPage.vue` reuse the same hub, focused editor, and action footer. Together they own 10 route entries in this inventory.
- `lib/components/workspace/content/TenantPageEditor.vue` owns both new and existing tenant page editing. It keeps page metadata and all blocks on one scrolling page, expands one block inline, saves the complete page document through the existing page endpoint, and guards route changes and locale switches when dirty.
- `lib/components/workspace/blog/BlogPostEditor.vue` owns both tenant blog editor states. It keeps the writing canvas visible, moves metadata into a settings slideover, serializes snapshot saves, detects version conflicts, and exposes publishing as a separate action.
- `components/products/ProductEditor.vue` owns the location product collection and item form. At this commit the item form remains a sibling of the full collection in a grid. On narrow viewports it still stacks below the collection rather than opening in a slideover.
- `lib/components/workspace/inbox/GuestThreadInbox.vue` owns six organization, site, location, and reservation routes. Conversations, media grids, analytics, onboarding, and other operational pages have specialized interaction needs and should remain named exceptions to any focused-field default.

Twenty of the 56 route files delegate to one of the repeated owners listed in the Shared canonical owners table. The remaining routes largely own their page-specific forms or overviews directly.

### Current editing and save models

| Route family | Current interaction | Canonical write behavior that the redesign must preserve |
|---|---|---|
| Organization, site, brand, and location settings | Hub plus focused detail, responsive split pane, footer Cancel and Save | Per-detail writes through the existing dashboard or editor endpoint, local dirty comparison, validation before save |
| Tenant pages | One continuous metadata and block canvas | Whole page `POST` or `PATCH`, block ordering, document-version concurrency, locale transition and route-leave guards |
| Tenant blog | Writing canvas plus settings slideover | Serialized snapshots, explicit lifecycle and publish operations, server and document version conflict handling |
| Products | Collection plus sibling item form | Item `POST`, `PATCH`, and `DELETE`; category and item move endpoints; existing media picker and price model |
| Q&A and testimonials | Collection and add or edit form on the same page | Item `POST`, `PATCH`, reorder or status actions, and `DELETE`; site and location Q&A currently duplicate the interaction locally |
| Links | Page metadata, all links, ordering, and preview on one continuous page | One page-level `PATCH` with a saved snapshot and route-leave guard |
| Onboarding and add-location | Multi-step workspace with live tenant preview | Existing site-creation and onboarding commands; the add-location route uses the `editor` layout rather than dashboard chrome |

### Packet evidence and open defects

- The packet is a historical visual baseline, not proof that every error still exists at this source commit.
- [Menu item edit form is unreachable on mobile](https://github.com/paulchrisluke/krabiclaw/issues/709) remains open, and the checked-out `ProductEditor.vue` still contains the sibling-grid root cause. This is valid redesign evidence.
- [Location Settings to Available features throws 500](https://github.com/paulchrisluke/krabiclaw/issues/720) and [Menu editor shows Invalid URL](https://github.com/paulchrisluke/krabiclaw/issues/723) remain open as tracker records, but commit `9f4a688f` adds source fixes for both. The packet still lacks successful post-fix captures, so its error screenshots must not become target-state references.
- Privacy exclusions cover member identities, guest names, messages, and reservation details. They remove screenshot evidence, not the routes themselves. The route inventory retains those owners and marks the packet evidence as excluded.

### Constraints for the next decisions

- Prototype the Page editor first. It is the clearest structural mismatch and its current save and concurrency contract is explicit.
- Treat `EditorPaneShell` and `EditorNavigationList` as the starting point for the focused-editor direction. Test whether they can deepen cleanly before proposing another shell.
- Decide editing patterns by manager shape. Settings fields, page blocks, long-form writing, product collections, media grids, and conversations do not need identical navigation.
- Keep all business writes on the current APIs and shared domain utilities. This inventory found no need for a redesign-specific API, state store, schema, or business model.
- Re-capture successful Products and Available features states before using those screens for visual acceptance. Source fixes alone do not prove the production-like dashboard experience.
